# Security

## 1. Scope

This document covers `cvx-vault-math-v1`, `cvx-api-vault-v1` and `cvx-vault-v1`. It states the trust model, the threats considered, the mitigation for each, and the test or proof that demonstrates it. Every threat maps to at least one test in `docs/TESTING.md`. Section 6 lists the questions that remain open before a production deployment.

## 2. Trust model

Canton and Ethereum differ in one fundamental way that users of an ERC-4626 vault must understand: on Canton, the vault's assets sit in an account at the underlying registry, and the vault's state is a contract signed by the operator.

**What the library guarantees**

- Every vault choice computes amounts exactly as `docs/MATH.md` specifies, rounds in favour of the vault, and moves value atomically with the accounting (SPEC §6).
- Through vault choices, a requester receives at least `minOut`, or nothing moves. The operator can bypass this for a live request outside every vault choice (**Pending requests**, below; T-21).
- No party other than the operator can change vault state, mint or burn shares, or move the vault's assets through the library.
- Requesters do not see each other's requests, allocations or holdings (D-15).

**What depends on the operator**

- **Custody.** The operator owns `vaultAccount`, and for both reference registries the operator can move the vault's underlying outside every vault choice:
  - TestTokenV2: a transfer with `actors = [operator]`, accepted by the receiver (`test_hazard_t10_operatorMovesCustody` in `test/vault-v1-test/daml/Cayvox/VaultV1Test/VaultHazards.daml` performs it).
  - Amulet: an `Amulet` is signed by the DSO and its owner ([`Amulet.daml` L160](https://github.com/canton-network/splice/blob/0.8.4/daml/splice-amulet/daml/Splice/Amulet.daml#L160)), and the transfer factory accepts the sender alone as actor ([`ExternalPartyAmuletRules.daml` L346-L349](https://github.com/canton-network/splice/blob/0.8.4/daml/splice-amulet/daml/Splice/ExternalPartyAmuletRules.daml#L346-L349); [`AmuletRules.daml` L204-L213](https://github.com/canton-network/splice/blob/0.8.4/daml/splice-amulet/daml/Splice/AmuletRules.daml#L204-L213)).

  Depositors therefore trust the operator with custody of the underlying. The library cannot prevent such a move; it makes it detectable, because the underlying registry reports the move for `vaultAccount` without a matching execution, and custody no longer reconciles with `totalAssets` (I-01; SPEC §8; T-10).
- **State integrity outside choices.** A signatory can archive its contract and create a replacement with different fields, bypassing every choice; canton-contracts states the same limit for its Pausable component ([`packages/security/api-pausable-v1/README.md` L121-L124](https://github.com/OpenZeppelin/canton-contracts/blob/aeca01d043311d8ccc8ab7cda4d7c16e682429fa/packages/security/api-pausable-v1/README.md#L121-L124)). The operator is the sole signatory of `VaultState`, so the operator can do this. The library makes it detectable: totals can be reconciled against share registry events (I-02) and underlying holdings (I-01) (`test_hazard_t11_operatorRewritesTotals`).
- **Liveness in Permissioned mode.** Requests execute only when the operator submits. In Permissionless mode, requesters execute their own requests (D-05).
- **Operator participant.** The operator signs `VaultState`, so its participant must confirm every execution, including a Permissionless one that the operator's application does not act on. Canton applies a signatory-based confirmation policy: the mediator requires a confirmation from the participants hosting each signatory of a contract involved in the transaction, and the transaction aborts when one is missing ([Canton documentation, smart contract consensus, confirmation policies](https://docs.canton.network/overview/reference/smart-contract-consensus)). An execution submitted while the operator's participant is unavailable therefore aborts and changes nothing (D-05). The requester signs its request alone (SPEC §2), so cancelling it does not need the operator's participant. How long the mediator waits for confirmations is a parameter of the synchronizer (§6).
- **Request allocations outside an execution.** The operator controls each request's `Request_Allocate` (`DepositRequest_Allocate` or `RedeemRequest_Allocate`; SPEC §4.2 names the pair this way), so it can exercise it outside a vault execution and create the requester's receipt allocation and, for an unfunded request, its funding allocation (`test_vault_delegationOutsideAnExecution` in `test/vault-v1-test/daml/Cayvox/VaultV1Test/VaultErrors.daml`). The request is one-shot: the choice is consuming, so it runs at most once (SPEC §4.2). Every allocation it creates is bound to the request, uncommitted and withdrawable by the requester, though the operator, the settlement's executor, can settle it in the same transaction first (T-21), and carries the request's deadline as its `settlementDeadline`, so any lock ends at that deadline (SPEC §4.2; `test_vault_delegationOutsideAnExecution` checks all three and withdraws both allocations).
- **Pending requests.** Every request settlement names the operator as its only executor (SPEC §4.2), and the vault makes a request's input and output legs atomic only inside its own choice. The operator can therefore settle a request's input leg alone, outside every vault choice: with a funded request's allocation, or with one it creates through `Request_Allocate`. The requester's input moves and no output is paid (T-21). A live request is thus a standing authorization of its `amount` to the operator until it executes, is cancelled with its allocations withdrawn, or reaches its deadline. The library cannot prevent this under D-04; it makes it detectable. A burned share input leaves `S` above the share supply (I-02). A deposited input appears in the underlying registry's events as a move into `vaultAccount` under the request's settlement, without a matching execution (SPEC §8). Requesters keep deadlines short and cancel requests that do not execute.

  How long a request is exposed depends on its funding; v1 keeps this design:
  - **Request-time funding**, a committed allocation made with the request, exists to give the operator certainty of funds. A committed allocation cannot be withdrawn before its deadline (`test_vault_cancel_committedFundingAfterDeadline` in `test/vault-v1-test/daml/Cayvox/VaultV1Test/VaultScenarios.daml`), so it stays settleable by the operator until its deadline, even after the request is cancelled. `test_hazard_t21_operatorSettlesInputAlone` settles such an allocation's input leg alone.
  - **Execution-time funding**, an unfunded request whose funding allocation the request's delegation creates inside the execution, leaves no allocation before the execution. The operator controls the delegation choice, so once the requester has handed it its holdings, as a Permissioned execution needs, the operator can still create the allocation outside an execution and settle the input alone, until the request is cancelled (`test_hazard_t21_executionTimeFunding_holdingsHanded`, with the `LoneSettler` fixture in `test/vault-v1-test/daml/Cayvox/VaultV1Test/Hostile.daml`).
  - **Execution-time funding in Permissionless mode.** The requester submits its own execution and never hands its holdings to the operator, so the operator cannot settle its input alone: it holds no allocation and cannot use the holdings (`test_hazard_t21_executionTimeFunding_permissionless`).

  A requester that does not want to rely on the operator for this step uses execution-time funding in Permissionless mode, and cancels a request it no longer wants. Whether the operator's participant can use a holding of the requester that it witnessed in an earlier execution, such as returned change, without the requester's disclosure is an open question (§6).
- **Registry migration.** `VaultState` records each registry's factories by contract ID, and no vault choice changes them. When a registry replaces its factory, every execution fails until the operator migrates the vault: it archives the state and creates it again with the new factory and every other field unchanged, or creates a new vault. v1 has no migration choice; one can be added later through Smart Contract Upgrade. Reconciliation tells a migration from T-11 by its totals, which do not change (`test_hazard_b04_registryMigration`). The operator never reuses the identifier of a retired vault for a new one: the share instrument and the requests' bindings follow the identifier, so the retired vault's shares and live requests would act on the new vault.
- **Disclosure.** A party can only disclose a contract it sees ([Canton documentation, ledger model, disclosure](https://docs.canton.network/overview/reference/ledger-model-detailed)). In Permissionless mode the operator must serve the current `VaultState`, the share registry's factory contract and, for redemptions, the vault account's input holdings; without them the requester cannot execute (SPEC §2; `test_vault_depositRedeem_permissionlessFunded` and `test_vault_depositRedeem_permissionlessUnfunded` pass them). A stale disclosure fails the submission and the requester retries against the successor (D-16).
- **Contention in Permissionless mode.** Every execution consumes the vault state, so at most one execution succeeds per state; a requester that keeps executing its own small requests makes others' submissions fail and retry until their deadlines pass (D-16). Nothing is lost. An operator that also executes in Permissionless mode, batching requests, bounds the effect.
- **Yield timing.** `Vault_AddAssets` raises the price in one step, so a requester can deposit just before a predictable addition and redeem just after; an addition on a tiny `S` makes one share unit worth much, and later deposits lose up to that much to rounding, which `minOut` bounds. Operators add yield in small, frequent steps, and only above a minimum `S`.
- **Ordering.** In a batch, the operator chooses the order, and order affects each request's price. `minOut` and `deadline` bound the effect for each requester.

**What the consuming application owns**: party hosting and authorization, admission policy in Permissioned mode, disclosure of vault state to requesters, participant configuration and package vetting. canton-contracts states the same scope for its library packages ([`SECURITY.md` L28-L31](https://github.com/OpenZeppelin/canton-contracts/blob/aeca01d043311d8ccc8ab7cda4d7c16e682429fa/SECURITY.md#L28-L31)).

## 6. Open questions before production use

Two questions are open before a production deployment. Neither changes the library's code; each bears on how a deployment is operated or on what a requester can rely on.

1. **Timing parameters of the target synchronizer.** The synchronizer the vault is deployed on, for example the Canton Network global synchronizer, sets its own dynamic parameters, among them the ledger time record time tolerance and the confirmation response timeout. The tolerance bounds how far record time may follow the ledger time at which the vault compares a request's deadline, and so how close to a deadline an execution can safely be submitted (T-08). The confirmation response timeout bounds how long an execution waits for the operator's participant before it aborts (§2, Operator participant). The rule for operators in T-08 has to be checked against these values for each deployment; they can be read from a participant connected to the synchronizer or from the configuration its operators publish.
2. **Witnessed holdings of a requester.** When the operator's participant takes part in a vault execution, it witnesses, as an informee, holdings of the requester that the execution creates, for example change returned to the requester. It is open whether the operator's participant can then use such a holding, without the requester's disclosure, to fund an allocation through a later request's delegation. On the in-memory ledger it cannot see such a holding. The guarantee of T-21 for execution-time funding in Permissionless mode (`test_hazard_t21_executionTimeFunding_permissionless`) assumes it cannot; the question is to be settled on Canton at the protocol versions in use (34 and 35), with the operator on its own participant.
